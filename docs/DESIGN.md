# 모아요 설계안

## 0. 배경과 확정된 사항
- 목표: 한국 가족(여러 명, 원화)이 함께 쓰는 가계부. 수동 입력이 기본이고, 영수증·캡처·결제문자를 던지면 AI가 정리해 준다. 나중에 안드로이드 앱을 붙여 알림을 자동 수집한다.
- 확정(질문 답변):
  - 레포는 `hackpoong/moayo` 입니다.
  - 로그인은 **Google**, 가족 합류는 **초대 링크**로 합니다.
  - 분류는 **카테고리 금액 분할 + 자유 태그**로 합니다. 지출 1건을 카테고리 여러 개로 금액을 나눌 수 있고(마트 10만 = 식재료 5만 + 의류 5만), 통계는 카테고리 기준입니다. 태그(#여행 #제주)는 금액 없이 여러 개 붙이는 가로지르는 라벨입니다.
  - AI 모델은 §6의 비교 결과를 보고 정합니다.

## 1. 스택 (비용 0원 가까이, 혼자 운영)
| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트 | Vite + React 19 + **TypeScript**, Tailwind v4, React Router, vite-plugin-pwa | 기존에 익숙한 스택 그대로입니다. 금융 데이터 모델이라 타입이 버그를 많이 막아 줍니다. PWA로 앱 껍데기를 캐시해서 바로 열립니다. |
| 로컬 우선 | **Dexie(IndexedDB)** + `useLiveQuery` | 가족의 전체 내역을 기기에 복제해 둡니다(몇 년 치여도 몇 MB). 목록·달력·통계·검색이 모두 로컬에서 계산되므로 화면을 넘길 때 네트워크를 기다리지 않습니다. |
| 백엔드 | **Supabase Free**: Postgres + Auth(Google) + Realtime + Storage + Edge Functions | 한 서비스에 인증, 행 단위 권한(RLS), 실시간 동기화, 파일 저장, 서버 함수가 다 들어 있습니다. 무료 티어는 DB 500MB, 저장소 1GB입니다. |
| 호스팅 | Netlify(지금 쓰는 방식) 또는 Cloudflare Pages, 둘 다 무료 | 정적 배포만 하면 됩니다. |
| 공유 로직 | `packages/core` (순수 TS) | 현금일 계산, 문자 파서, 중복 매칭 코드를 웹과 Edge Function(Deno)이 같이 씁니다. |
| AI | 업체별 어댑터 인터페이스, 환경변수로 선택 | §6 참고. 업체를 바꿔도 코드 수정이 거의 없습니다. |

동기화 엔진(PowerSync, InstantDB 등)은 붙이지 않고 직접 얇게 만듭니다. 가족 규모라 충돌이 드물고, 의존성과 유료 전환 위험이 줄어듭니다.
- 쓰기: 클라이언트가 UUID를 만들어 Dexie에 즉시 반영하고 outbox에 넣은 뒤 Supabase에 upsert합니다. 오프라인이면 나중에 다시 보냅니다.
- 읽기: 모든 행에 서버가 매기는 `updated_at`/`rev`와 `deleted_at`(삭제 표시)을 둡니다. 앱을 켤 때나 다시 볼 때는 커서 이후 변경분만 받아 오고(약간 겹치게 받아 누락을 막음), 그 밖에는 Realtime `postgres_changes`(household_id 필터)를 바로 적용합니다. 다른 가족 화면에는 1초 안팎으로 반영됩니다.
- 충돌: 행 단위로 마지막 쓰기가 이깁니다. 분할과 태그는 거래 행 안에 JSONB로 넣어서 한 덩어리로 함께 갱신됩니다.

## 2. 데이터 모델 (모든 테이블에 household_id, updated_at, deleted_at)
- `households`, `members`(user_id, display_name, role: owner/member), `invites`(code, 만료, 1회용)
- `payment_methods`: name, type(`cash|credit_card|check_card|bank_account|local_currency|gift_voucher|easy_pay`), issuer(BC, 현대 등), last4, owner_member_id, aliases[](문자 매칭용: "비씨", "농협BC"), billing(credit: 마감일, 결제일, 몇 달 뒤 결제인지), archived, sort. 사용자가 추가·수정할 수 있습니다. 기본값으로 현금, 여민전, 온누리상품권을 미리 넣어 둡니다.
- `categories`: name, kind(expense/income), icon, color, parent_id(선택), sort
- `tags`: name
- `transactions`:
  - id, kind(`expense|income|transfer`), status(`confirmed|review|canceled`), amount(원, 정수)
  - occurred_at(timestamptz, KST로 표시), cash_date(date, 저장할 때 계산), cash_date_override
  - merchant, memo, payment_method_id, member_id(쓴 사람), installment_months
  - splits JSONB `[{category_id, amount}]` (합계 = amount가 되도록 검증, 남는 금액은 '미분류'), tag_ids JSONB
  - approval_no, card_last4(매칭 단서), items JSONB(영수증 품목, 선택)
  - field_sources JSONB(필드마다 어느 출처에서 왔는지), linked_tx_id(취소↔원거래 연결)
  - created_by, created_at
- `raw_inputs` (원문 보존): source(`manual|image|screenshot|statement|sms|push|share`), raw_text, image_path(Storage), app_package, device_id, received_at, content_hash(같은 원문 재전송 방지), parser(`rule:shinhan_sms`, `llm:<model>`), parsed JSON, status
- `transaction_sources`: transaction_id, raw_input_id, candidate_index, action(`created|merged|duplicate|review`), filled_fields[]. 거래 하나에 출처 여러 개, 원문 하나(명세서)에 거래 여러 개가 연결됩니다.
- `transfer_rules`: 이름·계좌 패턴 → '이체'로 분류합니다. 대상은 가족 구성원끼리 송금, 본인 계좌 간 이체, 카드대금 출금, 페이·지역화폐 충전입니다.
- `merchant_rules`: 가맹점 → 기본 카테고리. 사용자가 고친 내역에서 학습합니다.
- `device_tokens`: 안드로이드 수집용. 구성원 1명에 묶이고, 해시로 저장하며, 수집 API만 쓸 수 있고, 폐기할 수 있습니다.

## 3. 날짜 기준 토글
- 발생일 기준은 `occurred_at`을 씁니다.
- 현금일 기준은 `cash_date`를 씁니다.
  - 현금, 체크카드, 계좌, 선불수단(여민전, 온누리, 페이머니)은 발생일과 같습니다. 선불은 충전할 때 돈이 나가지만, 충전은 '이체'로 두고 사용일을 현금일로 보는 쪽으로 단순화합니다.
  - 신용카드는 결제수단의 마감일·결제일 규칙으로 계산합니다.
  - 할부는 현금일 보기에서 N개월로 펼칩니다(조회할 때 계산하고, 나머지 원은 첫 달에 붙입니다).
  - 카드 명세서를 넣으면 실제 청구월로 덮어씁니다.
- 달력과 통계 화면 상단에 토글을 두고, 마지막에 고른 값을 기억합니다.

## 4. 수집 파이프라인 (이미지·텍스트·안드로이드가 모두 같은 입구)
Edge Function `ingest` 하나로 처리합니다. 웹 이미지 업로드, 웹 텍스트 붙여넣기, 안드로이드 알림이 전부 여기로 들어옵니다.
1. **인증**: 사용자 JWT 또는 device token으로 household를 확정합니다. 가족마다 하루 호출 상한을 둬서 AI 비용을 막습니다.
2. **원문 저장**: `raw_inputs`에 넣습니다. content_hash가 같으면 기존 결과를 그대로 돌려줍니다.
   - 이미지는 클라이언트가 긴 변 약 1500px JPEG로 줄여서 private Storage에 올립니다.
3. **파싱**:
   - 먼저 규칙 기반 파서로 처리합니다(주요 카드사 승인문자, 토스·카카오뱅크 푸시, 승인취소 문구). AI 비용이 들지 않고 빠르며 외부로 보내지 않아도 됩니다.
   - 실패하거나 이미지면 LLM에 구조화 출력(JSON 스키마)으로 보내 후보 배열을 받습니다.
   - 보내기 전에 카드번호와 계좌번호는 끝 4자리만 남기고 가립니다.
4. **정규화**: 금액은 정수로, 시간은 KST로 바꿉니다. 결제수단은 last4·별칭으로 찾습니다. kind는 지출, 수입, 이체, 취소 중 하나로 판정하고, transfer_rules와 merchant_rules를 적용합니다.
5. **매칭**: 후보마다 기존 거래와 점수를 냅니다.
   - 승인번호가 같으면 확정입니다.
   - 금액이 같아야 합니다.
   - 시간 근접도: 둘 다 시각이 있으면 ±10분, 날짜만 있으면 ±3일(명세서는 늦게 찍힘).
   - 결제수단이 서로 맞는지, 가맹점명이 비슷한지(정규화한 뒤 bigram 유사도. "스타벅스코리아"와 "스타벅스 세종점"을 같은 곳으로 봅니다)도 봅니다.
6. **결정**:
   - 점수가 높으면 **병합**합니다. 빈 필드만 채우고(덮어쓰지 않음), 출처를 연결하고, 필드 출처를 기록합니다.
   - 애매하면 `status=review`로 새로 만들고 '확인 필요' 함에 의심 대상과 함께 보여 줍니다.
   - 점수가 낮으면 새로 만듭니다.
   - 취소는 원거래에 연결해서 상쇄합니다.
7. **결과**: 응답은 `{created, merged, review}`입니다. 다른 기기에는 Realtime으로 전달됩니다. 웹에서는 결과를 시트로 보여 주고 바로 고치거나 되돌릴 수 있습니다. 확인 단계 때문에 입력이 막히지 않게 합니다.

## 5. 보안
- 모든 테이블에 RLS를 겁니다. `is_member(household_id)`(security definer)일 때만 읽고 쓸 수 있습니다. Storage 경로도 `{household_id}/...` 정책으로 막습니다.
- 초대 코드는 1회용이고 72시간 뒤 만료됩니다. 구성원을 내보내거나 역할을 바꾸는 것은 owner만 할 수 있습니다.
- AI 키는 Edge Function secret에만 두고 클라이언트에는 노출하지 않습니다.
- 무료 티어에는 자동 백업이 없습니다. 그래서 앱 안에 JSON/CSV 내보내기를 넣고, 선택적으로 주간 GitHub Action으로 `pg_dump`를 비공개 저장소에 쌓습니다.
- Supabase 무료 프로젝트는 7일 동안 활동이 없으면 일시정지됩니다. 매일 쓰면 문제없고, 필요하면 cron으로 깨워 둡니다.

## 6. AI 모델 비교 (영수증 1장 ≈ 입력 2.4K 토큰(이미지 약 1.6K 포함), 출력 약 0.4K로 추정)
| 모델 | 입력 / 출력 ($/1M) | 1장당 | 월 300장 | 학습 사용 |
|---|---|---|---|---|
| Claude Haiku 5.5 | 0.10 / 0.50 | 약 $0.0004 (약 0.6원) | 약 $0.13 | API 데이터는 학습에 쓰지 않음 |
| Gemini 2.5 Flash-Lite | 0.10 / 0.40 (출처마다 다름) | 약 $0.0004 | 약 $0.12 | 유료 API는 학습 안 함. **무료 티어는 학습에 쓰일 수 있음** |
| Gemini 3.5 Flash-Lite | 0.30 / 2.50 | 약 $0.0017 (약 2.4원) | 약 $0.5 | 위와 같음 |
| GPT-5.4 nano | 0.20 / 1.25 (공식 발표) | 약 $0.001 | 약 $0.3 | API 데이터는 기본적으로 학습에 쓰지 않음 |
| GPT-5 nano | 0.05 / 0.40 (비공식 집계) | 약 $0.0003 | 약 $0.1 | 위와 같음 |

- 결론: 어느 모델이든 **월 1달러 미만**이라 비용은 고르는 기준이 되지 못합니다. 기준은 **한국어 영수증·캡처 정확도**와 **데이터 정책**입니다. 금융 원문이 들어가므로 Gemini 무료 티어는 쓰지 않습니다. 이미지는 업체마다 토큰을 세는 방식이 달라서 실제 단가는 측정해 봐야 확정됩니다.
- 진행 방식:
  - 처음에는 **Claude Haiku 5.5**를 기본으로 둡니다(공식 단가가 가장 싸고 구조화 출력을 지원합니다. effort는 `low`로 둡니다).
  - 2단계에서 실제 영수증·캡처·문자 20~30건으로 평가셋을 만들고, Haiku 5.5, Gemini Flash-Lite, GPT nano를 같은 스키마로 돌려 정확도와 실측 비용을 표로 보여 드립니다. 그 결과로 최종 모델을 고릅니다.
  - 어댑터 구조라서 업체를 바꾸는 일은 환경변수 하나입니다.
- 단가 출처: Claude 단가는 Anthropic 기준이고, Gemini·OpenAI 단가 일부는 서드파티 집계입니다. 평가 전에 각 사 공식 요금표로 다시 확인합니다.

## 7. 지시서에서 빠졌거나 보완이 필요한 점
1. **이중 집계**: 카드대금 출금, 지역화폐·페이 충전, 본인 계좌 간 이체도 '가족 송금'과 같은 문제입니다. 그래서 '송금 제외' 규칙을 **이체(transfer) 종류**로 넓혀서 함께 처리합니다.
2. **할부, 승인취소, 부분취소, 환불**: 현금일 기준과 중복 판정에 직접 영향을 줍니다. 1~2단계에 포함합니다.
3. **중복을 조용히 버리면 위험합니다**: 같은 날 같은 금액으로 커피를 두 번 사는 일은 흔합니다. 확실한 경우만 자동으로 병합하고, 애매하면 '확인 필요' 함으로 보냅니다.
4. **'가족에게 한 송금'의 범위**: 가계부 구성원끼리는 이체로 보고, 부모님 용돈처럼 가계부 밖의 가족에게 보낸 돈은 보통 지출로 봅니다. 대상마다 규칙에서 고를 수 있게 합니다.
5. **누가 썼는지**: member_id로 기록하고 구성원별 통계도 냅니다. 개인 비공개 지출은 범위 밖입니다(필요하면 말씀해 주세요).
6. **여러 출처를 병합할 때의 우선순위**: 금액·시각은 문자와 푸시, 품목은 영수증, 청구일은 명세서를 믿습니다. 사용자가 직접 고친 값은 덮어쓰지 않습니다.
7. **안드로이드 SMS 권한**: Play 스토어는 기본 문자앱이 아니면 SMS 권한을 거의 허가하지 않습니다. 대신 **NotificationListener** 하나로 문자앱 알림, 카드앱 푸시, 토스 알림을 모두 받을 수 있습니다. 배포는 APK 직접 설치나 내부 테스트 트랙을 권합니다.
8. 이후 단계에서 권하는 기능: 예산, 고정지출·정기결제, 데이터 내보내기. 여민전 캐시백을 수입으로 기록할지도 그때 정합니다.

## 8. 화면과 UX
- 모바일: 하단 탭(홈, 내역, 달력, 통계, 더보기)과 가운데 **+** 버튼이 있습니다.
  - **+**를 누르면 금액 키패드가 먼저 뜨고, 이어서 카테고리, 결제수단을 고릅니다. 결제수단은 최근에 쓴 것을 맨 앞에 둡니다. 3번 탭이면 저장됩니다.
  - 같은 시트에서 📷 이미지와 📋 붙여넣기도 할 수 있고, 안드로이드 공유 메뉴로 들어오는 것도 받습니다.
- 데스크탑: 사이드바 + 목록과 상세를 나란히 보는 2단 화면입니다. 같은 컴포넌트로 반응형 처리합니다.
- 홈: 이번 달 지출·수입, 확인 필요 배지, 최근 내역을 보여 줍니다.
- 검색: 가맹점, 메모, 태그, 금액 범위, 결제수단, 구성원으로 로컬에서 바로 찾습니다.

## 9. 단계별 계획 (각 단계가 끝날 때 확인을 받습니다)
- **P0 기반**:
  - 새 레포를 `apps/web`, `packages/core`, `supabase/`(migrations, functions) 구조로 만듭니다.
  - 스키마와 RLS, Google 로그인, 가족 생성·초대·합류, PWA 껍데기, 기본 데이터, CI(lint, typecheck, vitest)를 준비합니다.
- **P1 MVP (수동 가계부)**:
  - 결제수단, 카테고리, 태그를 관리하는 화면을 만듭니다.
  - 빠른 입력, 분할, 태그, 이체 종류, transfer_rules, 할부, 현금일 계산을 넣습니다.
  - 내역, 달력, 통계(카테고리·구성원·결제수단, 기간), 검색, 날짜 기준 토글을 만듭니다.
  - Dexie 동기화와 Realtime, 오프라인 outbox, JSON/CSV 내보내기를 넣습니다.
- **P2 AI 입력**:
  - `ingest` 함수, 이미지·텍스트 입구, 주요 카드사·은행 문자와 푸시 규칙 파서를 만듭니다.
  - LLM 어댑터, 매칭·병합, 확인 필요 함, 가맹점 카테고리 학습을 넣습니다.
  - 모델 평가셋을 만들어 비교 리포트를 냅니다.
- **P3 자동 수집**:
  - device token 발급·폐기 화면, 수집 API 문서를 만듭니다.
  - Capacitor 안드로이드 앱을 만듭니다. 웹 번들을 앱에 포함하고, NotificationListener 플러그인, 앱별 허용 목록, 기기 오프라인 큐, 공유 인텐트를 넣습니다.
- **P4 다듬기**: 예산, 고정지출, 데스크탑 다듬기, 백업 자동화를 합니다.

## 11. 검증 방법
- `packages/core` Vitest: 현금일(마감·결제일, 월말, 할부), 문자 파서(카드사별 실제 문구 샘플), 매칭 점수(중복, 정당한 반복결제, 취소)를 테스트합니다.
- DB: 테스트 계정 두 가족을 만들어 다른 가족의 행과 Storage 파일에 접근할 수 없는지 RLS를 검증합니다(SQL 테스트).
- E2E: Playwright로 모바일 화면 크기에서 입력, 달력, 통계 흐름을 확인합니다. 브라우저 컨텍스트 두 개로 한쪽에서 입력하고 다른 쪽에 1~2초 안에 반영되는지 봅니다. 오프라인으로 입력한 뒤 다시 연결하면 동기화되는지도 봅니다.
- P2: 평가셋으로 추출 정확도(금액, 날짜, 가맹점, 결제수단)와 중복 판정 정확도를 표로 냅니다.
